# Як працюємо із задачами й Git

Це наш погоджений процес. Команди виконує користувач, асистент пояснює синтаксис, перевіряє спробу й нагадує про момент коміту.

## Одна задача

Перед початком визначаємо одну мету, файли, нове поняття, критерій готовності й майбутню назву коміту. Після реалізації перевіряємо результат та зміни у файлах, тоді комітимо.

Розмітка HTML/JSX і CSS разом утворюють верстку. Єдиного обов'язкового порядку для всіх команд немає. Для нашого інтерфейсу зазвичай ідемо так:

1. Сценарій: що людина хоче зробити й що означає успіх.
2. Мінімальні дані й контракт компонента: потрібні поля, props, типи.
3. Семантична розмітка, базовий CSS mobile-first та доступні елементи керування.
4. Поведінка: передавання даних, взаємодія, URL, потрібні стани.
5. Перевірка в браузері, `npm run check`, `npm run build` та доречні тести логіки.
6. Перегляд diff і один коміт зі зрозумілою метою.

Повернення між кроками нормальне: нова поведінка може потребувати іншої розмітки. Для ризиків бекенду (OTP, доступ до телефонів, бюджет) робимо окремі ранні експерименти за продуктовим планом.

## Коли комітити

Коміт — збережений у Git знімок підготовлених змін. Одна невелика завершена мета може охоплювати кілька файлів: тип, компонент, CSS і його перевірку. Окрема задача лише на оформлення або виправлення також може мати власний коміт.

Наші звичайні навчальні коміти робимо, коли результат працює, зрозумілий і проходить погоджені перевірки. Збереження файла не створює коміт. Локальний коміт не відправляє зміни на GitHub: для цього потрібен окремий `git push` після налаштування віддаленого репозиторію.

## Перший коміт

На початок цього уроку репозиторій не має комітів. Спочатку заверши поточну вправу: `name` і `speciality` вже передаються, залишилося показати їх у картці. Потім перевіримо результат і зробимо цілісний початковий знімок проєкту. Він міститиме каркас та першу демо-картку з props.

Після перевірки картки виконай:

```sh
npm run format
npm run check
npm run build
git status
git add .
git diff --cached --stat
git diff --cached
git commit -m "chore: initialize VarashWorks learning project"
git log --oneline -5
```

`git add .` тут готує весь початковий проєкт; `.gitignore` виключає залежності, кеші, `.env` і `.local` із резервними копіями. Перед `commit` переглянь список і вміст підготовлених файлів. Якщо після `add` змінив файл, додай його повторно.

`git diff --cached` показує саме те, що ввійде в коміт. Якщо перегляд відкрився на весь термінал, клавіша `q` виходить із нього. Для нового ще не доданого файла звичайний `git diff` не показує вміст — відкрий його або спочатку підготуй через `add`.

Якщо Git попросить ідентичність автора, задай власні значення лише для цього репозиторію й повтори коміт:

```sh
git config --local user.name "Твоє ім’я"
git config --local user.email "Твій email або GitHub noreply email"
```

## Наступні коміти

Після першого коміту для наступної задачі створимо окрему коротку гілку. Наприклад, для списку майстрів:

```sh
git switch -c codex/catalog-list
```

Після завершення задачі додавай конкретні файли або потрібну папку. Наприклад, якщо всі зміни цього модуля належать до поточної задачі:

```sh
git status
git diff
git add src/modules/catalog
git diff --cached
git commit -m "feat(catalog): render demo master list"
```

Повернення гілки в `main`, push і pull request розберемо після першого коміту. Файл GitHub CI вже підготовлений, але сам локальний коміт його не запускає.

## Назви комітів

Обираємо Conventional Commits як домовленість проєкту: `type(scope): коротка дія`. `scope` — необов'язкова назва частини проєкту. Пишемо англійською, щоб практикувати поширений у міжнародних командах формат; це не обов'язкова вимога Git.

| Тип        | Коли                           | Приклад                                     |
| ---------- | ------------------------------ | ------------------------------------------- |
| `feat`     | Нова можливість                | `feat(catalog): filter masters by category` |
| `fix`      | Виправлення помилки            | `fix(catalog): preserve selected category`  |
| `refactor` | Перебудова без зміни поведінки | `refactor(catalog): extract master card`    |
| `docs`     | Пояснення та документація      | `docs: explain local setup`                 |
| `chore`    | Обслуговування й інструменти   | `chore: configure code checks`              |
| `style`    | Форматування коду              | `style: format catalog components`          |

У нашій домовленості `style` означає форматування коду. Нове оформлення картки може бути `feat(ui)`, а виправлення зламаного відступу — `fix(ui)`: тип залежить від змісту зміни, а не розширення `.css`.
