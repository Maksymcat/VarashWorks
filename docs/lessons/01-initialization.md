# Урок 01. Як відкривається наша сторінка

**Час:** 5–10 хвилин. **Мета:** знайти місце для зміни тексту й стилю та пояснити шлях від адреси до екрана.

## 1. Простеж запит

Запусти `npm run dev` і відкрий `http://localhost:3000`.

1. Браузер запитує адресу `/` у локального сервера Next.js.
2. App Router знаходить `src/app/page.tsx`: назва `page` визначає сторінку маршруту.
3. `src/app/layout.tsx` обгортає її спільним каркасом через `children`. Тут живуть `<html>`, `<body>` і мова документа.
4. React описує вміст сторінки, а Next.js готує результат для браузера.
5. Браузер застосовує `globals.css` і стилі, імпортовані з `page.module.css`.

Це схема відповідальностей; вона не означає, що файли щоразу виконуються браузером у такому порядку.

## 2. Розбери основні поняття

**`.ts` і `.tsx`.** Обидва формати містять TypeScript. `.tsx` додатково дозволяє JSX — запис на кшталт `<h1>Майстри поруч</h1>`. TypeScript перевіряє очікувані типи значень до запуску, але не перевіряє автоматично дані, що колись надійдуть із мережі.

**Серверні компоненти.** У `app` компоненти за замовчуванням серверні. Для звичайного тексту й посилань не потрібен `"use client"`. Клієнтський компонент знадобиться, коли додамо стан React, обробники подій або браузерні API. Розберемо це на конкретній взаємодії.

**CSS Modules.** Імпорт `styles` із `page.module.css` дає об’єкт класів. Запис `className={styles.example}` пов’язує елемент із класом `.example`. Next.js створює окремі імена класів, щоб стилі різних компонентів не конфліктували. Глобальні правила залишаємо в `globals.css`.

**Mobile-first у CSS.** Базові правила описують вигляд на телефоні. Через `@media (min-width: 44rem)` додаємо зміни для ширших екранів, наприклад дві колонки замість однієї. Спочатку перевіряємо малий екран, потім розширюємо його.

## 3. Зроби дві маленькі зміни

Перед кожною зміною скажи своїми словами, що має змінитися в браузері.

1. У `page.tsx` знайди один видимий текст і зміни лише його. Якщо значення береться з `siteConfig`, відкрий `src/shared/config/site.ts` і зміни відповідне поле там. Збережи й перевір результат.
2. У `page.module.css` знайди клас цього елемента або його контейнера. Зміни один відступ, наприклад `padding`, на невелику величину. Почни з ширини 320–390 px у режимі пристрою браузера: перевір очікуваний простір, перенесення тексту й відсутність горизонтального прокручування. Потім перевір планшетну та настільну ширину.

Перейди між посиланнями клавішею `Tab`: фокус має бути помітним. Для елементів керування, якими користуються дотиком, орієнтуйся на область натискання від 44 × 44 px, де це доречно. Це практична ціль для зручності, а не заміна повної перевірки доступності.

Змінюй по одному значенню: так легше пов’язати причину й результат. Після вправи залиш бажаний варіант або поверни початкове значення.

## 4. Прочитай команди як інструменти

`package.json` — опис проєкту: що йому потрібно та які команди доступні. `package-lock.json` фіксує точні версії всього дерева залежностей. Обидва файли зберігаються разом; lock-файл не редагуємо вручну. `npm ci` встановлює саме за ним і повідомляє про невідповідність маніфесту.

Після змін виконай:

```sh
npm run check
npm run build
```

Якщо перевірка повідомила про форматування, виконай `npm run format`: за оформлення відповідає Prettier. Переглянь зміни й повтори `npm run check`. Помилку типів або Biome спочатку читаємо й розуміємо, а потім виправляємо. Biome перевіряє код і JSX, зокрема частину правил доступності; він не гарантує відповідності WCAG. Успішна збірка ще не перевіряє зручність інтерфейсу — для цього потрібен браузер.

## Коли урок засвоєно

Ти можеш знайти джерело видимого тексту, пояснити різницю між `layout` і `page`, передбачити одну CSS-зміну та розрізнити маніфест і lock-файл. Далі відкрий [урок 02](02-catalog.md): підготуєш тип даних і одного вигаданого майстра самостійно. Каталог і профіль поки є лише заготовками.
