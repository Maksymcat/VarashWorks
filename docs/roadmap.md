# Дорожня карта

Повне джерело вимог — [продуктовий план](product-plan.md), зокрема backlog у розділі 23.1. Тут фіксуємо найближчі кроки, щоб кожна зміна залишалася зрозумілою.

## Поточний етап: локальна основа

Працюємо над **частиною B03**: Next.js App Router, React, строгий TypeScript, CSS Modules, Biome для перевірки коду й JSX, Prettier для форматування, Node.js і npm. Підготовлено статичні сторінки та заготовки компонентів. Між маршрутами можна переходити; повного користувацького сценарію ще немає.

| Задача плану                | Стан і наступна дія                                                                 | Критерій готовності за планом                                |
| --------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| B01 — категорії й територія | Потребує розмов із першими майстрами; технічний макет не визначає фактичне покриття | Є перелік робіт і готові відповідні майстри                  |
| B02 — OTP й ціна доставки   | Відкладено до окремого малого експерименту з SMS-провайдером                        | Реальний код, повторний вхід, облік вартості й захист ліміту |
| B03 — основа й середовища   | Локальна частина в роботі; тестовий деплой попереду                                 | Збірка, типи й тестовий деплой без реальних даних            |

**B03 ще не завершено:** локальний запуск не замінює тестового розгортання. Сьогодні не підключаємо базу, SMS або хостинг.

### Локальна частина готова, коли

- Проєкт встановлюється через `npm ci` на вказаній версії Node.js.
- `npm run dev` відкриває стартову сторінку; на ширині 320–390 px немає горизонтального прокручування, текст і елементи керування вміщуються.
- `npm run check` і `npm run build` завершуються успішно.
- Видимі посилання працюють із клавіатури й мають помітний фокус; заголовки та мова документа відповідають вмісту.
- Ти можеш самостійно пояснити роль `layout.tsx`, `page.tsx` і CSS Module та виконати вправу з уроку 01.
- Відкриваються `/`, `/masters`, `/masters/example`, `/request` і `/for-masters`; для відсутнього маршруту є сторінка 404.
- Заготовки прямо пояснюють свій стан; немає активних форм чи обіцянки працюючих фільтрів. Навчальні сторінки мають `noindex`.

Це критерії перевірки, а не звіт про вже пройдені перевірки.

## Далі: ти реалізовуєш каталог по кроках

Кожна задача має одну мету, критерій готовності та запропоновану назву коміту. Порядок роботи й команди Git — у [короткій пам’ятці](git-workflow.md). Картку, список і профіль будуємо невеликими завершеними змінами; розмітку, CSS та поведінку узгоджуємо всередині кожної зміни.

Асистент підготував каркас та інструменти. Дані, фільтрацію, форми й іншу функціональність пишеш ти; допомога — пояснення, підказки та перевірка твоєї спроби. Нові інструменти фронтенду й бекенду розбираємо перед використанням.

| Майбутній малий крок                 | Що вчимо                                                                | Критерій готовності                                                                         |
| ------------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1. Один вигаданий майстер            | Тип об’єкта, потрібні поля, окремий файл даних                          | Ти створив тип і запис без реальних персональних даних; перевірка типів проходить           |
| 2. Дані в картці та список           | Props, масиви, повторне використання компонента                         | Картка відображає передані дані, список складається із записів                              |
| 3. Вибір послуги й населеного пункту | GET-форма, URL як стан, серверні `searchParams`                         | Фільтри дають відповідні картки або чесний порожній стан; оновлення сторінки зберігає вибір |
| 4. Справжній вміст профілю           | Динамічний маршрут, серверні `params`, пошук за `slug`, відсутній запис | Профіль відповідає адресі; невідомий `slug` дає 404                                         |

Функціональність із цієї таблиці ще не реалізована. Для першого видимого результату починаємо з маленької частини кроку 2: [урок 02](lessons/02-catalog.md), передати ім’я та спеціалізацію в одну картку через props. Після розбору цієї спроби винесемо повний тестовий запис в окремий файл і продовжимо кроки таблиці. Зараз користувач має лише одну поточну задачу.

Зберігаємо погоджений напрям: білий фон, синій акцент, чіткі картки й фільтри. **Mobile-first обов’язковий:** базові стилі для телефона, розширення через `min-width` для ширших екранів. Компоненти серверні за замовчуванням; клієнтський стан додамо, коли з’явиться взаємодія, яка його потребує.

Після навчального каталогу повертаємося до незавершеної частини B03 й залежностей продуктового backlog. **B04 і B05 не завершено:** база, міграції, фільтри та робочий каталог ще попереду. До реальних заявок потрібно виконати B01, B02 та решту відповідних P0-вимог плану. Метадані, семантика, доступність і швидкість закладають основу SEO; позиції в Google перевірятимемо після публікації, вони не гарантовані самим вибором фреймворку.

## Як закриваємо кожну наступну задачу

Наша Definition of Done — домовленість, що означає «готово»:

1. Сформульовано один видимий результат і пояснено, навіщо потрібна зміна.
2. Зміна невелика; її можна прочитати й пояснити без прихованої магії.
3. Сценарій спочатку перевірено на ширині 320–390 px, потім на планшеті й комп’ютері. Перевірено видимий фокус із клавіатури та, де доречно, області натискання від 44 × 44 px. Для логіки з ризиком помилки додано доречну автоматичну перевірку.
4. Проходять `npm run check` і `npm run build`.
5. Переглянуто різницю у файлах; у документації зафіксовано нове рішення або обмеження, якщо воно з’явилося.
6. Асистент повідомив, що результат готовий до коміту, запропонував назву й пояснив команди; користувач зафіксував зміни у Git. Перший коміт міститиме весь потрібний початковий проєкт після завершення поточної вправи з props.

Не додаємо інструмент заради самого інструмента: кожна залежність має вирішувати поточну зрозумілу задачу.
